### 2.2 Dual-Engine LLM Client Factory (`get_llm_client`)

Supports dynamic switching between **Cloud LLM (Groq)** and **Local LLM (Ollama / OpenAI-compatible endpoint)**:

```python
# Local LLM Settings
LOCAL_LLM_URL = os.getenv("LOCAL_LLM_URL", "http://localhost:11434/v1")
LOCAL_LLM_MODEL = os.getenv("LOCAL_LLM_MODEL", "llama3.2:3b")
LOCAL_LLM_API_KEY = os.getenv("LOCAL_LLM_API_KEY", "ollama")

def get_local_llm_client() -> Tuple[Any, str]:
    global _local_llm_client
    if _local_llm_client is None:
        from openai import OpenAI
        _local_llm_client = OpenAI(base_url=LOCAL_LLM_URL, api_key=LOCAL_LLM_API_KEY)
    return _local_llm_client, LOCAL_LLM_MODEL

def get_groq_client(agent_name: str) -> Tuple[Groq, str]:
    if agent_name == "query":
        return Groq(api_key=GROQ_KEY_QUERY), GROQ_MODEL_QUERY
    elif agent_name == "context":
        return Groq(api_key=GROQ_KEY_CONTEXT), GROQ_MODEL_CONTEXT
    elif agent_name == "synthesis":
        return Groq(api_key=GROQ_KEY_SYNTHESIS), GROQ_MODEL_SYNTHESIS
    return Groq(api_key=GLOBAL_GROQ_KEY), "openai/gpt-oss-120b"

def get_llm_client(agent_name: str, provider: str = "groq") -> Tuple[Any, str]:
    if (provider or "").lower() == "local":
        try:
            return get_local_llm_client()
        except Exception as exc:
            print(f"[Local LLM Warning]: {exc}. Falling back to Groq client.")
            return get_groq_client(agent_name)
    return get_groq_client(agent_name)
```

**Key Capabilities:**
- **Dynamic Routing:** Every node (`query_specialist_node`, `context_auditor_node`, `response_synthesizer_node`) reads `state["llm_provider"]` and resolves the appropriate client.
- **Resilient Fallback:** If local Ollama server is unreachable, automatically logs a warning and falls back to Groq Cloud.
- **Trace Tagging:** Every agent node attaches provider information (`provider: "local"` or `"groq"`) and model name to `AgentTraceItem["details"]` and trace label.

### 2.3 Complete State Schema Definitions

```python
class CandidateContext(TypedDict):
    source: str      # Exact URL or "Chroma Document #1" or "BMU Curated Knowledge Base"
    url: str         # Source URL
    content: str     # Raw scraped text (<3500 chars) or bundled summaries
    score: float     # Hybrid retrieval score (0.0 to 1.0)
    type: str        # "scraped_page" | "stored_summary"

class AgentTraceItem(TypedDict):
    agent: str              # Identifier (e.g. "Agent 1 (QuerySpecialist) [Local Ollama]")
    latency_ms: float       # Execution duration in milliseconds
    details: Dict[str, Any] # Step-specific metadata (provider, model, keywords, decisions, reasons)

class BMURAGState(TypedDict):
    raw_query: str          # Original question submitted by user
    llm_provider: Optional[str] # "groq" | "local" (injected by API request)
    
    # Agent 1 outputs
    optimized_query: str    # Semantically enriched query for vector retrieval
    keywords: List[str]     # 3-5 extracted core keywords
    intent_category: str    # "admissions" | "courses" | "fees" | "hostels" | "placements" | "faculty" | "campus" | "general"
    
    # Retrieval Tool outputs
    candidates: List[CandidateContext] # Pre-fetched extraction candidates (up to 3)
    current_candidate_idx: int         # Pointer tracking which candidate Agent 2 is inspecting
    
    # Agent 2 outputs
    audit_decision: Literal["SUFFICIENT", "TRY_FALLBACK", "NOT_FOUND"]
    audit_reason: str       # Justification sentence from auditor
    vetted_context: str     # Approved text payload passed to Agent 3
    
    # Agent 3 outputs
    final_answer: str       # Natural language answer generated for student
    top_results: List[Dict[str, Any]] # Top URLs with similarity scores
    
    # Observability
    agent_trace: List[AgentTraceItem] # Chronological trace sequence for UI & Phoenix
    error: Optional[str]
```

### 2.4 Node 1: Agent 1 - Query Specialist (`query_specialist_node`)

#### Pure Logic & Responsibility
Translates ambiguous, acronym-heavy student queries into dense, entity-rich queries suitable for vector retrieval, and identifies intent categories.

- **Groq Client & Configuration:**
  - Env Var: `GROQ_API_KEY_QUERY_AGENT` (fallback: `GROQ_API_KEY`)
  - Model: `openai/gpt-oss-20b`
  - Temperature: `0.1` (low variance, near-deterministic)
  - Max Tokens: `600`
- **System Prompt:**
  `"You are a specialized academic query optimizer for BML Munjal University. Output strictly valid JSON."`
- **Transformation Prompt Logic:**
  1. Enforces acronym expansion: `B.Tech` -> `B.Tech Computer Science and Engineering CSE`, `BMU` -> `BMU BML Munjal University`, `fees` -> `fees tuition fee structure`.
  2. Strips conversational fluff (`"Can you tell me..."`, `"I was wondering..."`).
  3. Formulates a JSON schema response:
     ```json
     {
       "optimized_query": "...",
       "keywords": ["...", "..."],
       "intent": "admissions | courses | fees | hostels | placements | faculty | campus | general"
     }
     ```
- **Robust JSON Extraction (`_safe_json_parse`):**
  Uses regex `r"```(?:json)?\s*(\{.*?\})\s*```"` to unpack code fences, falling back to `r"(\{.*\})"` for unformatted JSON, and parsing via `json.loads()`.
- **Heuristic Deterministic Fallback (Fault Tolerance):**
  If Groq fails, returns empty, or errors out:
  1. Stopword filter: Strips common English stopwords (`what`, `are`, `the`, `and`, `for`, `with`, `from`, `at`, `is`, `in`, `of`, `to`, `how`, `can`, `does`, `which`).
  2. Extracts terms of length > 2 as keywords (up to 5).
  3. Intent matching rules (applied only if LLM returned `"general"`):
     - Contains `fee`, `fees`, `cost`, `scholarship` -> `"fees"`
     - Contains `eligibility`, `admission`, `criteria`, `apply` -> `"admissions"`
     - Contains `b.tech`, `cse`, `mba`, `course`, `program` -> `"courses"`
     - Otherwise -> `"general"`
- **Trace output:**
  Agent name: `"Agent 1 (QuerySpecialist)"`, details include `model`, `optimized_query`, `keywords`, `intent`.

### 2.5 Node 2: Multi-Candidate Retrieval & Extraction Tool (`retrieval_tool_node`)

#### Pure Logic & Responsibility
Retrieves candidate documents, performs hybrid ranking, and constructs candidate contexts.

1. **Primary Retrieval Path (HTTP Microservice):**
   - Sends HTTP POST to `http://127.0.0.1:8001/retrieve` with `{"query": optimized_query, "top_k": 8}` and a 10-second timeout.
   - Extracts ranked results: `[{"summary": ..., "url": ..., "score": ...}, ...]`.
   - On non-200 response: records `retrieval_warning` with HTTP status and response text, switches to fallback.
2. **In-Process Resilient Fallback:**
   - If the microservice is down, unreachable, or times out, it switches `retrieval_mode` to `"in_process_fallback"`.
   - Lazily loads local `SentenceTransformer("all-MiniLM-L6-v2")` and `chromadb.CloudClient` via `get_chroma_and_embedder()`.
   - Embeds query: `query_emb = embedder.encode([opt_query]).tolist()`.
   - Queries collection `bmu_summaries` for up to 16 nearest neighbors (expanded pool for hybrid re-ranking).
   - Calculates normalized hybrid score for each document:
     $$\text{HybridScore} = 0.68 \times (1.0 - \text{distance}) + 0.32 \times \text{KeywordScore}$$
     where `KeywordScore` executes:
     - **Acronym Normalization:** Normalizes academic variants (`b.tech`, `b-tech`, `b tech` $\rightarrow$ `btech`; `m.tech` $\rightarrow$ `mtech`; `mba` $\rightarrow$ `mba`; `cse` $\rightarrow$ `cse`).
     - **Stopword Filtration:** Removes conversational fillers (`what`, `is`, `are`, `tell`, `how`, etc.) to prevent false overlaps on lengthy blog articles.
     - **Morphological Stemming:** Stems domain terms (`fees`/`tuition` $\rightarrow$ `fee`; `hostels` $\rightarrow$ `hostel`; `admissions` $\rightarrow$ `admission`; `courses` $\rightarrow$ `course`).
     - **Canonical URL Authority Scaling:** Evaluates text + URL tokens. Canonical portal directories (`/courses/`, `/fee-structure/`, `/admission/`) receive a $1.25\times$ multiplier; marketing blogs (`/social/`, `/blogs/`) receive a $0.65\times$ damping factor.
   - Sorts results by score descending.
3. **Threshold Gate (`0.10`):**
   - If `top_score < 0.10`, the query is flagged as low similarity, skipping live web scraping and candidate construction.
   - However, `top_results` is still populated with documents that have `score > 0` (from the first 3 ranked results).
4. **Candidate Context Construction Pipeline:**
   - **Candidate 1 & 2 (Live Web Pages):**
     - Extracts the URL from the top 2 ranked documents.
     - Uses `trafilatura.fetch_url(url)` followed by `trafilatura.extract(downloaded)`.
     - Boilerplate removal: Trafilatura strips navigation bars, footers, headers, ads, and sidebars.
     - If extracted text length > 100 chars, truncates to 3,500 characters and labels as `"scraped_page"`.
     - If the fetch fails or the page returns a 404/403/captcha, it falls back to the stored ChromaDB summary (`"stored_summary"`).
   - **Candidate 3 (Synthesized Knowledge Bundle):**
     - Merges the summaries of the top 6 ChromaDB documents into a unified multi-document context bundle separated by `---` delimiters.
     - Format: `"Source [URL]:\n{summary}"` for each document.
     - Uses the score and URL from the top-ranked document.
     - Serves as the ultimate fallback if specific scraped pages are missing details or broken.
- **Trace output:**
  Agent name: `"Tool (HybridRetrieval & MultiSourceExtractor)"`, details include `retrieved_count`, `prepared_candidates`, `top_score`, `retrieval_mode`, `microservice_url`, and optionally `retrieval_warning`.

### 2.6 Node 3: Agent 2 - Context Auditor (`context_auditor_node`)

#### Pure Logic & Responsibility
Validates factual sufficiency of the current candidate context against the user question before passing it to synthesis.

- **Groq Client & Configuration:**
  - Env Var: `GROQ_API_KEY_CONTEXT_AGENT` (fallback: `GROQ_API_KEY`)
  - Model: `openai/gpt-oss-20b`
  - Temperature: `0.1`
  - Max Tokens: `600`
- **System Prompt:**
  `"You are the BMU Context Relevance Auditor. Output strictly valid JSON."`
- **Context Truncation:**
  The context excerpt sent to the LLM is truncated to **2,500 characters** (`content[:2500]`), regardless of the full candidate content length.
- **Decision Taxonomy:**
  1. `SUFFICIENT`: The context directly and factually answers the question.
  2. `TRY_FALLBACK`: The context lacks the answer, but further candidate sources remain uninspected.
  3. `NOT_FOUND`: The context proves the information does not exist or all sources are exhausted.
- **Dual-Level Heuristic Fallback:**
  **Level 1 — When LLM returns empty or ambiguous decision:**
  - Extracts query words > 3 characters
  - Checks word overlap with candidate content
  - If >= 2 matching words AND content > 300 chars → `SUFFICIENT` with reason `"Heuristic acceptance: verified factual match on {words}"`
  - If it's the last candidate → `NOT_FOUND` with reason `"Heuristic fallback: exhausted candidates without sufficient match."`
  - Otherwise → `TRY_FALLBACK` with reason `"Heuristic fallback: checking next candidate source."`

  **Level 2 — When it's the last candidate AND verdict is `TRY_FALLBACK`:**
  - Re-runs the same word overlap check
  - If >= 2 words match AND content > 300 chars → upgrades to `SUFFICIENT` (`"Conclusive acceptance on final candidate bundle"`)
  - Otherwise → `NOT_FOUND` (`reason + " (Exhausted all candidate sources)."`)
- **Trace output:**
  Agent name: `f"Agent 2 (ContextAuditor - Candidate #{idx+1})"` — includes the candidate number dynamically. Details include `model`, `candidate_source`, `decision`, `reason`.

### 2.7 Conditional Routing & Autonomous Self-Correction Loop

#### `route_after_context_audit(state: BMURAGState) -> str`
```python
decision = state.get("audit_decision", "NOT_FOUND")
if decision == "SUFFICIENT":
    return "synthesize"          # Routes to response_synthesizer_node
elif decision == "TRY_FALLBACK":
    return "advance_candidate"    # Routes to advance_candidate_node (loop)
return "handle_not_found"         # Routes to handle_not_found_node
```

#### Self-Correction Loop Math
1. `advance_candidate_node`:
   $$\text{new\_idx} = \text{current\_candidate\_idx} + 1$$
2. Edge: `advance_candidate` points back to `context_auditor`.
3. The graph loops dynamically:
   - Candidate 1 (Scraped URL 1) -> `TRY_FALLBACK`
   - Candidate 2 (Scraped URL 2) -> `TRY_FALLBACK`
   - Candidate 3 (Chroma Summary Bundle) -> `SUFFICIENT` -> `response_synthesizer`
   - Or if all fail -> `NOT_FOUND` -> `handle_not_found`.

### 2.8 Node 4: Authoritative Not Found Handler (`handle_not_found_node`)

Executes when information is confirmed missing in BMU records:
- Returns an official referral rather than a generic model hallucination:
  `"I could not find sufficiently relevant information in official BML Munjal University records for this query. Please check the official BMU portal (https://www.bmu.edu.in) or contact the admissions office at info@bmu.edu.in / 1800-103-6888."`
- Sets `agent_trace` agent to `"RefusalHandler (Records Not Found)"` with action `"Authoritative BMU Helpdesk Referral"`.
- Latency: `0.0` ms (no external calls).

### 2.9 Node 5: Agent 3 - Academic Response Synthesizer (`response_synthesizer_node`)

#### Pure Logic & Responsibility
Generates a grounded academic response strictly faithful to `vetted_context`.

- **Groq Client & Configuration:**
  - Env Var: `GROQ_API_KEY_SYNTHESIS_AGENT` (fallback: `GROQ_API_KEY`)
  - Model: `openai/gpt-oss-120b` (Largest parameter model for structured reasoning and synthesis)
  - Temperature: `0.2` (Constrained factual adherence)
  - Max Tokens: `800`
- **System Prompt:**
  `"You are the official BMU Academic Assistant. Answer strictly from context."`
- **Synthesis Rules:**
  1. Direct statement of facts with structured bullet points for fees, eligibility, and dates.
  2. Zero extrapolation: If an exact detail is absent, state that it is not specified in the current records.
  3. No raw markdown headers (`#` or `##`), ensuring clean typography in the chat bubble UI.
- **Error Handling:**
  On exception: `f"Unable to generate response due to service error: {exc}"`.
- **Trace output:**
  Agent name: `"Agent 3 (ResponseSynthesizer)"`, details include `model` and `answer_length`.

### 2.10 Graph Compilation & Topology

```python
def create_bmu_rag_graph():
    workflow = StateGraph(BMURAGState)

    # Add Nodes
    workflow.add_node("query_specialist", query_specialist_node)
    workflow.add_node("retrieval_tool", retrieval_tool_node)
    workflow.add_node("context_auditor", context_auditor_node)
    workflow.add_node("advance_candidate", advance_candidate_node)
    workflow.add_node("handle_not_found", handle_not_found_node)
    workflow.add_node("response_synthesizer", response_synthesizer_node)

    # Linear Edges
    workflow.set_entry_point("query_specialist")
    workflow.add_edge("query_specialist", "retrieval_tool")
    workflow.add_edge("retrieval_tool", "context_auditor")

    # Conditional Branching
    workflow.add_conditional_edges(
        "context_auditor",
        route_after_context_audit,
        {
            "synthesize": "response_synthesizer",
            "advance_candidate": "advance_candidate",
            "handle_not_found": "handle_not_found",
        },
    )

    # Self-correction loop
    workflow.add_edge("advance_candidate", "context_auditor")

    # Terminal edges
    workflow.add_edge("response_synthesizer", END)
    workflow.add_edge("handle_not_found", END)

    return workflow.compile()

# Global compiled app (instantiated at module import)
bmu_rag_app = create_bmu_rag_graph()
```

### 3.7 Output Guardrail Logic (`validate_output`)

#### Grounding Verification Formulation:
$$\text{overlap} = \text{Tokens}_{\ge 4 \text{ chars}}(\text{Answer}) \cap \text{Tokens}_{\ge 4 \text{ chars}}(\text{Context})$$
$$\text{overlap\_ratio} = \frac{|\text{overlap}|}{\max(1, |\text{Tokens}_{\ge 4 \text{ chars}}(\text{Answer})|)}$$
$$\text{grounding\_score} = \min(1.0, \max(0.2, \text{overlap\_ratio} \times 1.2))$$

**Special Case:** If the answer contains `"not found in context"` (case-insensitive), grounding score is forced to `1.0` regardless of actual overlap.

#### Cloud API Output Question Schema:
```python

    "source_context": context[:3000],  # Note: 3000-char truncation, different from Agent 2's 2500
    "generated_answer": answer,

    "is_grounded": Noul(instructions="Is the generated answer strictly faithful to the provided context..."),
    "is_safe": Noul(instructions="Is the generated answer safe, polite, and free of sensitive disclosures..."),
}
```

#### Policy Routing:
1. **Safety Check:** If $P(\text{safe}) < 0.60 \implies$ Action: `block` (Withholds response).
   - Returns: `"[Response withheld by safety guardrail due to potential content policy violation.]"`
2. **Hallucination Detection:** If $P(\text{grounded}) < 0.40 \implies$ Action: `flag_disclaimer`.
   - Appends contextual verification disclaimer:
     `"*(Note: Please verify specific figures or dates directly on the official BMU portal at [URL].)*"`
3. **Verified Grounded:** If $P(\text{grounded}) \ge 0.40 \implies$ Action: `pass`.

## 5. Standalone Retrieval Engine & Microservice (`retrieval_service.py`)

Runs on port 8001 during local multi-service development, and executes directly in-process during unified cloud deployment (`semantic.py`).

### 5.0 Zero-PyTorch Cloud Memory Optimization (ONNX Runtime)

In previous iterations, the retrieval layer relied on `sentence-transformers` and `torch`. In 512MB cloud container environments (such as Render Free Tier), PyTorch imports alone consumed ~450MB–540MB, causing fatal `Out of memory (used over 512Mi)` kills.

The engine is modernized with **ChromaDB's native ONNX Runtime MiniLM engine (`ONNXMiniLM_L6_V2`)**:
* **Memory Footprint:** Baseline RAM drops from **~540MB to ~150MB** (operating safely under Render's 512MB cap).
* **Package Overhead:** Eliminates 1.5GB+ of PyTorch binaries from the build cycle, cutting Render deploy times from 7 minutes to **~45 seconds**.
* **Vector Equivalence:** Generates 100% mathematically identical 384-dimensional dense vectors against the existing `bmu_summaries` collection.
* **Fallback Resilience:** `get_embedder()` dynamically initializes the ONNX wrapper, retaining local `SentenceTransformer` as a fallback only if explicitly installed.

### 5.1 Hybrid Ranking Formulation

The retrieval engine balances semantic conceptual matching with exact lexical token overlap:

$$\text{SemanticSimilarity} = \max(0.0, 1.0 - \text{ChromaDistance})$$
$$\text{KeywordScore} = \frac{|\text{Tokens}(\text{Query}) \cap \text{Tokens}(\text{Document})|}{|\text{Tokens}(\text{Query})|}$$
$$\mathbf{FinalScore} = \mathbf{0.68} \times \text{SemanticSimilarity} + \mathbf{0.32} \times \text{KeywordScore}$$

- **Semantic Weight (0.68):** Handles synonyms, paraphrasing, intent matching (e.g. "what is the price" -> "tuition fees").
- **Keyword Weight (0.32):** Ensures exact acronyms and program codes (e.g. "CSE", "MBA", "B.Tech", "NIRF") receive top ranking over generic university pages.

### 5.2 Dual-Engine Support

| :--- | :--- | :--- |
| Key | `"minilm"` | `"voyage"` |

## 6. Knowledge Ingestion Microservice & Web Crawler (`ingestion_service.py`)

Runs on port 8002. Handles crawling, text extraction, semantic chunking, and vector indexing.

### 6.1 Web Crawler (`BMUWebCrawler`)
- **Domain Constraint:** Whitelisted strictly to `*.bmu.edu.in`.
- **Extension Filter (17 types):** Rejects `.pdf`, `.jpg`, `.jpeg`, `.png`, `.gif`, `.svg`, `.css`, `.js`, `.zip`, `.tar`, `.gz`, `.mp4`, `.mp3`, `.doc`, `.docx`, `.xls`, `.xlsx`.
- **User-Agent:** `Mozilla/5.0 (Windows NT 10.0; Win64; x64) BMU-IngestionBot/1.0`.
- **Request Timeout:** 12 seconds.
- **URL Normalization:** Resolves relative URLs against base, forces HTTPS, strips query strings and fragments, lowercases netloc, removes trailing slashes.
- **Link Extraction Regex:** `r'href=["\'](/[^"\'#\s>]+|https?://(?:www\.)?bmu\.edu\.in[^"\'#\s>]*)["\']'`
- **Title Extraction:** Matches `<title>...</title>`, strips whitespace, removes `|–-` suffixed substrings.
- **Trafilatura Options:** `include_comments=False`, `include_tables=True`, `no_fallback=False`, `favor_recall=True`.
- **Minimum Content Length:** 80 characters (pages with less are skipped).
- **Crawl Algorithm:** BFS using `collections.deque`, `visited` set for cycle prevention, discovers links only if more pages are needed.

### 6.2 Text Cleaning & Chunking (`chunk_document`)
- **Cleaning:** Strips non-printable control characters `[\r\t\f\v]`, collapses 3+ newlines to 2, collapses 2+ spaces to 1.
- **Chunk Parameters:**
  - `chunk_size`: 800 characters (configurable 300-2000 per request)
  - `chunk_overlap`: 150 characters (configurable 50-500 per request)
- **Paragraph & Sentence Boundaries:**
  - Iterates over paragraphs separated by `\n\n`.
  - When a paragraph exceeds `chunk_size`, splits using regex sentence lookbehind `(?<=[.!?])\s+`.
  - Re-injects overlapping trailing text (last paragraph of previous chunk if ≤ `chunk_overlap` chars).
- **Minimum Chunk Length:** 60 characters (trivial fragments discarded).
- **Chunk ID Format:** `f"voyage_{url_hash}_{idx:03d}"` where `url_hash` = first 10 chars of SHA-256 of the URL.
- **Chunk Metadata:** `id`, `text`, `url`, `title`, `chunk_index`, `total_chunks`, `content_hash`, `char_length`, `timestamp` (UTC ISO), `model`.

### 6.3 SHA-256 Deduplication
$$\text{Hash} = \text{SHA-256}(\text{normalize}(\text{chunk\_text}))$$
Normalization: `" ".join(text.strip().lower().split())` — lowercased, whitespace-collapsed.

Before sending chunks to Voyage AI, the system checks whether the chunk ID already exists in the ChromaDB collection. Redundant chunks are skipped, saving API credits and avoiding duplicate vector collisions.

### 6.4 Ingestion Pipeline (`ingest_document_chunks`)
1. Fetch existing IDs from ChromaDB collection
2. Filter out chunks whose IDs already exist (unless `force_refresh=True`)
3. Embed remaining chunks via `voyage_client.embed_documents(texts, batch_size=16)`
4. Index into ChromaDB in batches of **32** (different from embedding batch of 16)
5. Returns: `total`, `indexed`, `skipped`, `embedding_latency_ms`, `sample_ids`, `status`

## 10. Research Foundation & Data Pipeline: 5-Stage Summarization Evolution, Hybrid v5 Algorithmic Logic & Corpus Ingestion

### 10.1 Academic & Empirical Provenance (The 27-Page BMU Chatbot Research Report)

The production corpus underlying the BMU Website Chatbot (`bmu_summaries` collection, containing **1,258 indexed webpage summaries**) represents the culmination of extensive NLP research and empirical experimentation documented across a 27-page technical research report.

Institutional university websites present unique challenges for traditional RAG systems:
1. **High Structural Noise:** Raw university pages are saturated with boilerplate navigation headers, recursive dropdown menus, legal disclaimers, contact footers, and complex tabular syllabus structures.
2. **Context Window Contamination:** Ingesting raw HTML or uncurated text chunks inundates the vector space with repetitive tokens, driving up LLM token latency, incurring storage bloat, and degrading retriever precision.
3. **Factual Sensitivity:** Academic queries (cutoffs, scholarship percentage brackets, fee refund rules) tolerate zero hallucination; summarizing must preserve ground-truth institutional veracity verbatim.

To solve this, the project systematically explored, evaluated, and iterated through **five distinct generations of summarization architectures** before converging on the **Hybrid Extractive Summarizer (v5)**.

---

### 10.2 Evolutionary Progression: All 5 Explored Summarization Architectures

As documented in the project report (Pages 25–26), the summarization pipeline progressed through five iterative methodologies:

| Iteration / Technique | Theoretical Mechanism & Implementation | Empirical Strengths | Fatal Flaws & Failure Modes | Architectural Decision / Outcome |
| :--- | :--- | :--- | :--- | :--- |
| **1. TextRank** | Graph-based ranking inspired by Google PageRank. Constructs an undirected weighted graph where nodes represent sentences and edges represent lexical overlap (e.g., BM25 or normalized token intersection). Iterative random walks compute eigenvector centrality until graph convergence. | Unsupervised, domain-independent; identifies structurally central sentences in continuous discourse prose. | **Catastrophic failure on tabular & listed data.** BMU academic pages are dominated by syllabus tables, fee schedules, and bulleted admission requirements lacking natural discourse transitions. Graph connectivity broke down, assigning artificial weights to transitional filler phrases. | **Rejected** due to inability to parse semi-structured institutional catalogs and tables. |
| **2. Frequency-Based Summarization (TF / TF-IDF)** | Statistical term-frequency scoring. Computes word frequencies across the document, assigns sentence scores based on cumulative high-frequency token sums, and selects top-ranking sentences. | Extremely fast, zero GPU requirement, simple baseline. | **Semantic blindness and lexical redundancy.** Favors repetitive words (e.g., "university", "bmu", "engineering") without capturing thematic intent. Extracted disjointed sentence fragments with high lexical overlap but poor informational breadth. | **Explored as baseline only; rejected** for production due to redundancy and lack of semantic depth. |
| **3. Single-Sentence Semantic Summarization** | Dense neural embeddings. Encodes sentences using a Transformer encoder into high-dimensional vector space. Computes the document vector and extracts the single sentence with the highest cosine similarity to the document representation. | High semantic fidelity; identifies the global thematic thesis of the document with zero keyword matching fragility. | **Extreme information bottleneck.** BMU institutional pages are multi-faceted (e.g., a single engineering page outlines eligibility criteria, entrance test cutoffs, annual tuition, and laboratory infrastructure). Condensing this into exactly one sentence caused unacceptable information loss. | **Improved semantic relevance over baselines, but rejected** as overly restrictive for multi-intent institutional retrieval. |
| **4. Multi-Sentence Dynamic Summarization** | Multi-vector dense extraction. Encodes all candidate sentences, ranks them by semantic proximity to the document vector, and dynamically selects the top $k$ highest-scoring sentences ($k \ge 3$). | Expanded coverage across multiple subtopics; eliminated the single-sentence information bottleneck. | **High semantic redundancy (near-duplicate extraction).** Because ranking was independent per sentence, the model frequently selected 3 sentences stating virtually identical concepts (e.g., three consecutive phrasing variations of B.Tech JEE Main cutoff requirements), leaving no budget for fees or curriculum details. | **Proved the viability of dense multi-sentence selection, but motivated the critical need for redundancy elimination.** |
| **5. Hybrid Summarizer (v5)** *(Final Production Approach)* | Synergistic multi-stage pipeline: Regex sentence boundary segmentation $\to$ 384-dim dense Transformer encoding $\to$ Document-centroid cosine ranking $\to$ Greedy dissimilarity redundancy pruning ($\tau = 0.75$) $\to$ Cardinality selection ($K=3$) $\to$ Rule-based symbolic compression. | **Optimal balance of factual coverage, zero redundancy, and ultra-high information density.** Captures disparate facets (eligibility, fees, syllabus) while strictly preventing repetitive text. Achieves ~16x text compression without factual distortion. | None identified within the extractive problem domain. Operates deterministically, rapidly, and without GPU generative overhead. | **Adopted as final production engine** for indexing all 1,258 BMU website documents into `bmu_summaries.csv` and ChromaDB Cloud. |

### 10.3 Extractive vs. Abstractive Summarization: Pure Theoretical Foundation

A foundational tenet of the BMU Chatbot architecture is the strict, deliberate boundary between **Extractive Ingestion** and **Abstractive Synthesis**:

```
[ Raw Webpage Text ]
        │
        ▼ (Offline / Ingestion Pipeline)
[ Hybrid Extractive Summarizer v5 ]  <── Pure Extractive (Zero Hallucination, verbatim extraction)
        │
        ▼ 16x Compression
[ bmu_summaries.csv / ChromaDB Cloud ]
        │
        ▼ (Query-Time Retrieval @ Port 8001)
[ Top-k Relevant Candidates ]
        │
        ▼ (Query-Time Synthesis @ Port 8000)
[ Groq LLM (Agent 3: ResponseSynthesizer) ] <── Abstractive Natural Language Generation
        │
        ▼
[ Grounded Answer to User ]
```

#### 1. Extractive Summarization (The Ingestion Guarantee)
- **Definition:** The summarizer identifies, extracts, and concatenates exact, verbatim sentence spans already present in the source HTML document. It does not introduce novel vocabulary, rephrase syntax, or generate synthetic clauses.
- **Why Mandatory for BMU Knowledge Indexing:** Academic institutions operate under strict regulatory, financial, and legal policies. Abstractive summarizers (e.g., sequence-to-sequence neural models like BART, PEGASUS, or T5) are inherently prone to subtle hallucinations, token drift, and number swaps (e.g., accidentally altering an eligibility threshold from "60% aggregate" to "65% aggregate" or misrepresenting fee refund dates). The Hybrid v5 summarizer guarantees **100% factual fidelity** because every indexed token is a direct, unmodified quotation from official BMU publications.

#### 2. Abstractive Summarization (The Generative Paradigm)
- **Definition:** Uses generative sequence-to-sequence neural networks or autoregressive Large Language Models to read the source text and generate novel phrasing, reworded syntheses, and newly formed natural language sentences conveying the core ideas.

#### 3. Demystifying the Term "Hybrid" in this System
- In popular literature, "hybrid summarization" sometimes denotes an extractive selector followed by an abstractive paraphraser.
- **In this architecture and research report, "Hybrid" strictly denotes the combination of multiple complementary extractive methodologies:**
  $$\text{Hybrid} = \underbrace{\text{Dense Transformer Semantic Geometry}}_{\text{Representation}} + \underbrace{\text{Centroid Mean Vector Cosine Ranking}}_{\text{Salience}} + \underbrace{\text{Greedy Maximum Dissimilarity Pruning}}_{\text{Diversity}} + \underbrace{\text{Symbolic Rule-Based Filtering}}_{\text{Syntactic Compression}}$$
- The summarizer itself **never generates new sentences**.

#### 4. Separation of Ingestion Summarization vs. Runtime Generation
- **Offline / Ingestion:** No Large Language Model (LLM) is used to construct or store summaries in the vector database. The offline pipeline runs exclusively on `all-MiniLM-L6-v2` dense embeddings, vector algebra, and regex rules.
- **Runtime / Inference:** The Groq-hosted LLM (`llama-3.3-70b-versatile` / `gpt-oss-120b` / `llama3-70b-8192`) is invoked strictly at inference time by **Agent 3 (`ResponseSynthesizer`)** within the LangGraph graph (`bmu_rag_graph.py`). Agent 3 takes the verified, extracted context audited by Agent 2 and synthesizes a fluent, natural language answer for the student.

### 10.4 The Final Hybrid Summarizer (v5): Pure Algorithmic & Mathematical Specification

The Hybrid Summarizer (v5) operates across six deterministic, mathematically defined stages (Report Pages 12, 15–16):

```
Raw Webpage Text
      │
      ▼ Stage 1
[ Sentence Segmentation ] ──> Regex boundary split: (?<=[.!?])\s+
      │
      ▼ Stage 2
[ Sentence Embeddings ]   ──> all-MiniLM-L6-v2 (384-dim dense vectors, L2 normalized)
      │
      ▼ Stage 3
[ Centroid Calculation ]  ──> Compute mean vector c = (1/N) ∑ e_i; Rank by cos(e_i, c)
      │
      ▼ Stage 4 & 5
[ Greedy Selection & ]    ──> Top candidate selected; subsequent candidates admitted iff
[ Redundancy Pruning ]        max cos(e_k, e_j) ≤ 0.75; halt when exactly K = 3 sentences
      │
      ▼ Stage 6
[ Rule-Based Compression] ──> Whitespace collapse, stopword trimming, formatting cleanup
      │
      ▼
Compact Extractive Summary (Stored in Vector DB)
```

#### Stage 1: Regex Sentence Boundary Segmentation
Raw crawled text $T$ from Trafilatura is stripped of raw markup and partitioned into an ordered set of candidate sentences $S = \{s_1, s_2, \dots, s_N\}$ using a lookbehind regex boundary:
$$\text{Boundary Pattern} = \texttt{(?<=[.!?])\textbackslash s+}$$
Sentences with length below a noise threshold ($|s_i| < 15$ characters) or containing purely navigation tokens are discarded prior to embedding.

#### Stage 2: Dense Semantic Sentence Embeddings
Every valid candidate sentence $s_i \in S$ is mapped into a continuous 384-dimensional dense semantic vector space using the pre-trained `sentence-transformers/all-MiniLM-L6-v2` bi-encoder:
$$\mathbf{e}_i = \text{Embed}(s_i) \in \mathbb{R}^{384}$$
All vectors are $L_2$-normalized such that $\|\mathbf{e}_i\|_2 = 1.0$.

#### Stage 3: Document-Centroid Calculation & Relevance Ranking
The global semantic theme of the document is captured by computing the document centroid $\mathbf{c} \in \mathbb{R}^{384}$, defined as the unweighted arithmetic mean of all sentence embeddings in that document:
$$\mathbf{c} = \frac{1}{N} \sum_{i=1}^N \mathbf{e}_i$$
The relevance score of each individual candidate sentence $s_i$ is computed as its cosine similarity to the document centroid $\mathbf{c}$:
$$\text{score}(s_i) = \cos(\mathbf{e}_i, \mathbf{c}) = \frac{\mathbf{e}_i \cdot \mathbf{c}}{\|\mathbf{e}_i\|_2 \|\mathbf{c}\|_2}$$
Because all $\mathbf{e}_i$ are $L_2$-normalized, this reduces to:
$$\text{score}(s_i) = \frac{\mathbf{e}_i \cdot \mathbf{c}}{\|\mathbf{c}\|_2}$$
The candidate set $S$ is then sorted in descending order of relevance score to yield the ranked candidate queue:
$$Q = \langle s_{(1)}, s_{(2)}, \dots, s_{(N)} \rangle \quad \text{where} \quad \text{score}(s_{(1)}) \ge \text{score}(s_{(2)}) \ge \dots \ge \text{score}(s_{(N)})$$

#### Stage 4 & 5: Greedy Redundancy Elimination & Cardinality Selection ($K=3$)
To prevent near-duplicate information from consuming the summary budget, a greedy Maximum-Marginal-Relevance-style selection algorithm is executed with a redundancy threshold $\tau = 0.75$:

1. Initialize the selected set $S_{\text{selected}} = \emptyset$.
2. The highest-ranked candidate $s_{(1)}$ is unconditionally admitted:
   $$S_{\text{selected}} \leftarrow \{ s_{(1)} \}$$
3. Iterate sequentially through remaining candidates $s_{(m)} \in Q$ ($m = 2, 3, \dots, N$):
   - Compute maximum cosine similarity between candidate $s_{(m)}$ and all already selected sentences:
     $$\text{sim}_{\max}(s_{(m)}, S_{\text{selected}}) = \max_{s_j \in S_{\text{selected}}} \cos(\mathbf{e}_{(m)}, \mathbf{e}_j)$$
   - **Diversity Check:**
     $$\text{If } \text{sim}_{\max}(s_{(m)}, S_{\text{selected}}) \le \tau \ (0.75): \quad S_{\text{selected}} \leftarrow S_{\text{selected}} \cup \{ s_{(m)} \}$$
     $$\text{If } \text{sim}_{\max}(s_{(m)}, S_{\text{selected}}) > \tau \ (0.75): \quad \text{Discard } s_{(m)} \text{ (redundant)}$$
4. **Cardinality Halt:** The iteration terminates the moment $|S_{\text{selected}}| = 3$ (or when candidate queue $Q$ is completely exhausted).

#### Stage 6: Rule-Based Syntactic & Structural Compression
The 3 selected sentences undergo deterministic post-processing:
1. **Whitespace Normalization:** Consecutive spaces, tab characters, and trailing newline sequences are collapsed into single space delimiters (`re.sub(r'\s+', ' ', text).strip()`).
2. **Stopword & Boilerplate Stripping:** A compact, predefined catalog of academic boilerplate prefixes (e.g., "Click here to read more", "Read more at:", "BMU Official Portal -") and standalone filler stopwords are stripped.
3. **Punctuation & Delimiter Balancing:** Unpaired quotation marks or trailing hyphens resulting from table clipping are sanitized to preserve clean token boundaries for vector ingestion.

### 10.6 Topic Modeling Metadata Layer: LDA vs. BERTopic

During the research phase, topic modeling was evaluated to enrich document metadata and provide thematic categorization alongside dense vector embeddings:

#### 1. Latent Dirichlet Allocation (LDA) Configuration
- **Model:** Gensim / Scikit-Learn Latent Dirichlet Allocation.
- **Topics ($K_{\text{topics}}$):** 10 distinct topical clusters (e.g., Admissions & Cutoffs, Engineering Curriculum, Management Studies, Hostel & Campus Life, Placement Statistics, Research & Innovation, Executive Education, International Collaborations, Fee Structures & Scholarships, Student Welfare).
- **Random State:** `42` (ensures identical Dirichlet prior distributions across executions).
- **Representation:** Top 6 salient probability tokens per topic.

#### 2. Architectural Role
LDA was **not** used as the sentence selection mechanism; rather, it was implemented as an orthogonal **thematic metadata layer** to categorize the 1,258 scraped pages into high-level institutional buckets.

#### 3. Trade-Off Analysis: Why LDA was Retained over BERTopic
While **BERTopic** was evaluated for its state-of-the-art transformer-based clustering (c-TF-IDF over HDBSCAN clusters), the research team **deliberately retained LDA** for production deployment:
- **Computational Footprint:** LDA executes in seconds on standard CPU hardware without GPU requirements, whereas BERTopic introduces substantial clustering overhead (UMAP dimension reduction + HDBSCAN density clustering).
- **Deterministic Reproducibility:** LDA with fixed seed (`random_state=42`) produces 100% deterministic, stable topic assignments across runs, eliminating UMAP stochasticity.
- **Fast Metadata Ingestion:** For a corpus of 1,258 documents, LDA provided sufficient thematic separation with minimal operational complexity.

### 10.8 Production Indexing Implementation (`vector.py`)

This is the **original one-time ingestion script** that converted `bmu_summaries.csv` into the production ChromaDB Cloud `bmu_summaries` collection:

```python
import os
import pandas as pd
from sentence_transformers import SentenceTransformer
import chromadb
from tqdm import tqdm

csv_path = os.getenv("CSV_PATH", "bmu_summaries.csv")
df = pd.read_csv(csv_path)


model = SentenceTransformer("all-MiniLM-L6-v2")

client = chromadb.CloudClient(
    api_key=os.getenv("CHROMA_API_KEY"),
    tenant=os.getenv("CHROMA_TENANT"),
    database=os.getenv("CHROMA_DATABASE"),
)

collection = client.get_or_create_collection(name="bmu_summaries")

batch_size = 32
for i in tqdm(range(0, len(df), batch_size), desc="Indexing BMU Summaries"):
    batch = df.iloc[i:i+batch_size]
    documents = batch["Summary"].fillna("").tolist()
    urls = batch["URL"].fillna("").tolist()
    embeddings = model.encode(documents).tolist()
    ids = [f"id_{j}" for j in range(i, i + len(documents))]
    metadatas = [{"url": url} for url in urls]
    collection.add(
        documents=documents,
        embeddings=embeddings,
        metadatas=metadatas,
        ids=ids
    )
```

**Key Execution Parameters:**
- **Source CSV:** 1,258 records with columns `Summary` and `URL`.
- **Vector Embedding:** 384 dimensions generated via `all-MiniLM-L6-v2`.
- **Primary Keys:** Deterministic sequential format `id_0`, `id_1`, ..., `id_1257`.
- **Metadata Fields:** `{"url": url}` attached to every vector.
- **Batch Size:** 32 records per ChromaDB Cloud API transaction with `tqdm` progress monitoring.

## 11. Evaluation & Benchmarking Engines

### 11.1 Answer Quality Evaluation (`evaluate_metrics.py`)

Computes 5 quality metrics on a 0.00 to 5.00 scale:

1. **Relevance:**
   $$\text{Score} = 5.0 \times \left(0.6 \times \frac{|\text{Tokens}_Q \cap \text{Tokens}_A|}{|\text{Tokens}_Q|} + 0.4 \times \text{CosineSim}_{\text{TF-IDF}}(Q, A)\right)$$
2. **Faithfulness:**
   $$\text{Score} = 5.0 \times \left(0.5 \times \frac{|\text{Tokens}_A \cap \text{Tokens}_{\text{Ctx}}|}{|\text{Tokens}_A|} + 0.5 \times \text{CosineSim}_{\text{TF-IDF}}(A, \text{Ctx})\right)$$
   When `ground_truth` is provided, source = `context + " " + ground_truth`.
3. **Completeness:**
   Blends query token coverage with ground-truth TF-IDF support.
   - Without ground truth: pure query coverage
   - With ground truth: `0.6 × query_coverage + 0.4 × CosineSim(Answer, GroundTruth)`
4. **Conciseness (Length Penalty Step Function):**
   - $\le 25$ words $\to 5.0$
   - $\le 45$ words $\to 4.0$
   - $\le 70$ words $\to 3.0$
   - $\le 100$ words $\to 2.0$
   - $\le 140$ words $\to 1.0$
   - $> 140$ words $\to 0.0$
   - $= 0$ words $\to 0.0$
5. **Correctness:**
   $$\text{Score} = 5.0 \times \left(0.4 \times \text{TokenOverlap}(A, \text{Ref}) + 0.6 \times \text{CosineSim}_{\text{TF-IDF}}(A, \text{Ref})\right)$$
   Reference = `ground_truth` or `context` (whichever is available).

**Final Score:** Arithmetic mean of all 5 metrics.

**Helper Functions:**
- `normalize_text()`: Collapses whitespace
- `tokenize()`: Extracts alphanumeric tokens, lowercased
- `safe_cosine_similarity()`: TF-IDF vectorizer with English stop words, clamped to [0, 1]
- `get_ground_truth_from_url()`: Fetches URL, extracts with Trafilatura, returns normalized text
- `load_text_arg()`: Loads from file path or treats as raw text

**CLI Interface:**
```bash
python evaluate_metrics.py --context "..." --question "..." --answer "..." --url "..." --format json|table
```

## 14. Multi-Process Launcher (`run.bat`)

Orchestrates local developer bootup and shutdown in Windows environments:

1. **Dependency Verification:** Runs `pip install -r requirements.txt --quiet`.
2. **Port Conflict Clearance:**
   ```powershell
   Get-NetTCPConnection -LocalPort 8000,8001,8002,6006 | ForEach-Object { Stop-Process -Id $_.OwningProcess -Force }
   ```
   Followed by a 2-second `timeout /t 2` delay.
3. **Concurrent Process Spawning** (each in minimized window):
   - Phoenix on port 6006: `python phoenix_service.py`
   - Retrieval Service on port 8001: `python retrieval_service.py`
   - Ingestion Service on port 8002: `python ingestion_service.py`
   - Backend Orchestrator on port 8000: `python semantic.py`
4. **Health Check Polling Loop:**
   Polls `/health` endpoints on ports 8001, 8002, and 8000 (NOT 6006) with a 3-second sleep interval across up to 12 attempts (36-second safety timeout).
5. **Frontend Launch:**
   Opens `frontend\index.html` directly in the default browser (`start "" "frontend\index.html"`). No HTTP server is started for the frontend.
6. **Interactive Teardown:**
   Blocks on `pause >nul`. Upon keypress, cleanly kills all processes across ports 8000, 8001, 8002, and 6006.

> **Note:** Step numbering in the batch file is inconsistent: `[1/3]`, `[2/4]`, `[3/4]`.

## 17. Guardrail Bypass & Unconstrained LLM Generation

### Architecture
When `enable_guardrails=False` is passed from the frontend toggle:
1. **JEV Input Guardrail Bypass:** `jev_guardrail.validate_input(query)` is skipped entirely. Scope checking and toxic/injection heuristics are silenced.
2. **Autonomous Retrieval & Context Auditing:** LangGraph agents attempt institutional retrieval.
3. **Unconstrained Direct Answer Fallback:** If `audit_decision == "NOT_FOUND"` or context is irrelevant (e.g., cooking recipes, creative writing, general facts), `_generate_unconstrained_answer(query, provider)` calls the active model (Groq or Ollama) directly with an unconstrained system prompt instead of returning an academic scope refusal.
4. **Provenance Metadata:** Response returns `guardrail.status = "bypassed"` and `guardrails_enabled = False`.
5. **Arize Phoenix Spans:** Traces are emitted to Phoenix (`http://localhost:6006`) with `guardrails.enabled = False` and `response.source = "unconstrained_llm"`.
